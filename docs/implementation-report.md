## 1. 背景与目标

需求来自用户引用的 ChatGPT 对话《窃听风云男主介绍》（2026-10-28）。用户确定项目名 Wiesler、采用 Rust，并要求同时观察本地网络与代理。本文将对话中的建议整理为工程方案；对话中的示例日志和代码不是实测结果。

核心场景是客户端流式响应中断：用户希望知道哪个程序在连接什么目标、经过什么代理规则和链路，以及异常最早在哪一段被观察到。产品应提供可追溯的时间线，而不是根据一条报错自动判定代理节点或服务端责任。

第一阶段回答：Mihomo 是否可观测、哪些连接被观察到、连接计数与字节数如何变化、哪些时间段存在采集空白。后续逐步加入进程归属、报文级事件和应用日志，提升定位能力。

## 3. 现有项目与技术核实

已查看 GitHub 上的现成项目，作为架构选型依据：

| 参考 | 已有能力与借鉴范围 | 本项目决策 |
| --- | --- | --- |
| [bandwhich](https://github.com/imsnif/bandwhich) | 按进程、连接、远端地址显示带宽，结合抓包与系统进程信息 | 参考进程关联思路，Wiesler 优先做代理事件与故障时间线 |
| [Mihomo](https://github.com/MetaCubeX/mihomo) | 现有代理核心及控制器接口 | 通过公开接口观察独立运行的核心，不内嵌代理或改写网络路径 |

本次没有复制上述项目源码；这些链接是调研引用，不构成代码复用声明。实际复用时再按具体文件记录来源、版本与许可证要求。

核实结果：

- `/connections` 支持 HTTP GET 和 WebSocket，返回连接元数据、规则与代理链；鉴权使用 Bearer header。详见 [Mihomo API 文档](https://wiki.metacubex.one/api/)。
- WebSocket 也周期性调用 Snapshot，并非逐连接生命周期事件流；提高刷新频率只能缩小遗漏窗口。详见 [connections.go](https://github.com/MetaCubeX/mihomo/blob/Meta/hub/route/connections.go)。
- Windows 的 `GetExtendedTcpTable` 可按地址族读取带 PID 的 TCP 表，但它不提供 HTTP 请求边界或断流原因。详见 [Microsoft 文档](https://learn.microsoft.com/en-us/windows/win32/api/iphlpapi/nf-iphlpapi-getextendedtcptable)。

以上为 2026-10-29 查阅的在线文档及代码；实现适配器时还需记录用户实际 Mihomo 版本并验证返回样本。

## 4. 实施阶段与验收

| 阶段 | 工作内容 | 完成条件 |
| --- | --- | --- |
| P0：本次准备 | 架构、依赖锁定、CLI 骨架 | 本机构建、格式和静态检查通过，文档明确未实现能力 |
| P1：Mihomo MVP | 只读 GET 采集、快照差分、控制器健康、SQLite、JSONL 导出 | 正常连接可回放；控制器中断形成缺口而非批量断流；重启不会串联旧会话 |
| P2：进程与日志 | Windows TCP 表、应用日志导入、连接关联；随后适配 Debian | 缺失 PID、PID/端口复用、并发连接都有明确处理，关联保留证据与不确定性 |
| P3：按需报文证据 | Npcap/libpcap、回环与物理网卡、TCP FIN/RST、可见 DNS | 受控环境可识别所见报文及接口，采集丢包有记录；不能据单个 RST 指认根因 |
| P4：可视化与扩展 | Tauri 或本机 Web、更多代理适配器、WebSocket 快照 | 时间线与 CLI 数据一致；界面故障不影响采集和原有联网 |

P1 内部按“事件契约 → 快照解析 → 差分状态机 → 存储与回放 → 实机验收”顺序推进。先用 1 秒 HTTP 轮询降低调试复杂度，再按测得开销决定是否加入 250 毫秒 WebSocket 模式。两种方式都保留采样限制。

## 5. 验证方案

### 自动验证

后续实现测试围绕会改变诊断结果的场景：首次快照、空列表、字段缺失、重复 ID、认证失败、超时、坏 JSON、恢复后的基线重建、计数回退、重启与会话隔离。测试通过只证明这些输入下的行为。

数据库验证覆盖事务失败、异常退出后的可读性、迁移失败保留原库、导出与事件引用的一致性。关联验证覆盖显式代理、TUN、直连、IPv4/IPv6、共享代理隧道和多个候选匹配。

### 实机验收

在自有测试程序和隔离代理配置上做实验，避免中断正在运行的真实工作：

1. 发起一条正常长连接，记录应用、代理、系统采集的可用证据与时间。
2. 仅让测试控制器不可达，业务路径保持工作，验证只产生采集异常。
3. 在独立测试链路中制造连接终止，验证实际终止证据与采集异常可以区分。
4. 用相同事件日志重放报告，检查每条诊断均能追溯到事件 ID。
5. 经用户选择再观察 Codex 的真实断流；应用日志未接入时不声称识别了具体请求或响应正文。

Windows 首先验收；Debian 后续独立构建与实机验收。没有 Linux 环境实测时，不将“设计跨平台”写成“已支持跨平台”。

## 6. 关键边界与风险

- 代理连接消失只说明下一份有效快照不再包含它，不能等同 TCP reset 或请求失败。
- 控制器无法访问不等同代理转发失效；健康状态按数据源记录。
- 一个 HTTP/2 或代理复用连接可能承载多个请求；请求级结论需要应用证据。
- 系统表、代理内层连接和隧道外层连接的五元组可能不同；关联允许一对多和未知，不用时间接近强行配对。
- 默认不解密 TLS、不注入证书、不修改代理配置；抓包不能保证还原 HTTPS、QUIC 或加密 DNS 的内部行为。
- 依赖、协议和平台信息可能变化。按锁文件重现本次构建；新增依赖前重新核实来源和构建行为。
